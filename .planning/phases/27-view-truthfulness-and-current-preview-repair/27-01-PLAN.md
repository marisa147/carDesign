# Phase 27 Plan: View Truthfulness And Current Preview Repair

## Scope

Fix the current side/front/rear/top preview controls so they represent actual template/view capability. This phase addresses VIEW-01 and VIEW-02 only. It must not create the GR86/BRZ package or broaden the template catalog.

## Requirements Addressed

- VIEW-01
- VIEW-02

## Implementation Steps

1. Inspect the current Workbench preview flow and template metadata path.
   - Read first: `apps/web`, `services/core/src/caragent_core/generation/templates.py`, template catalog API/client helpers, and generated frontend contracts used by the preview panel.
   - Identify the component that owns the `侧面` / `前视` / `后视` / `俯视` controls and the source object used to render the selected version preview.

2. Add or derive a template view capability model.
   - If existing template/catalog/version payloads already expose available views, normalize that shape for the frontend.
   - If not, add a minimal typed capability field such as available view ids and missing view ids to the template/PreviewSpec response path.
   - Preserve side-only generic template compatibility: available views must include `side`; missing views must include `front`, `rear`, and `top`.

3. Update the Workbench preview controls.
   - Keep the four controls visible.
   - Selecting an unavailable view must render an empty-state panel containing exactly `模板未提供该视图`.
   - Do not reuse the side-view generated image when the selected view is unavailable.
   - Show available/missing view state in a way that is visible before or during review, not hidden in debug metadata only.

4. Add focused regression coverage.
   - Add frontend/unit tests for side-only view capability behavior.
   - Add core/API tests only if backend/template contracts change.
   - Assert `模板未提供该视图` appears for front/rear/top on side-only templates.
   - Assert side view still renders the real generated image and PreviewSpec overlays.

5. Run targeted verification first, then broader validation if the code changes are non-trivial.
   - Prefer the narrowest web test command for the touched component.
   - Run generated contract checks if API/core schema changes are made.
   - Run `pnpm validate` when feasible after focused tests pass.

## Acceptance Criteria

- `VIEW-01` is satisfied: switching views no longer shows fake front/rear/top renderings for side-only templates.
- `VIEW-02` is satisfied: users can tell which views the selected template/version provides.
- The frontend source contains the exact user-facing text `模板未提供该视图`.
- Side-only generic templates still support normal side-view generation and review.
- Tests cover at least one side-only template state and verify unavailable view behavior.

## Verification

- Focused frontend tests for the preview/view capability component.
- Backend/core tests for template view metadata only if backend contracts are touched.
- Contract generation/check if OpenAPI or shared type contracts change.
- `pnpm validate` if the local environment permits the full suite.

## Execution Notes

- Keep changes narrowly scoped to view truthfulness.
- Do not implement Phase 28 GR86/BRZ assets in this phase.
- Do not hide the unavailable view controls; the product decision is to keep them visible and truthful.
- Preserve existing job polling, artifact content rendering, PreviewSpec overlays, and GPT/provider behavior.
