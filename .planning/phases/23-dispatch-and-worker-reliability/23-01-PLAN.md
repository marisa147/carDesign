# Phase 23 Plan: Dispatch And Worker Reliability

## Scope

Implement the minimum reliable generation dispatch path:

1. Add `generation_jobs.state_version`.
2. Add `job_dispatch_outbox` with pending/dispatched/failed delivery metadata.
3. Replace direct enqueue during generation/iteration/retry creation with transactional outbox creation plus after-response dispatch.
4. Make worker claim `queued -> running` through a conditional update.
5. Split the generation worker into committed stages so `running` and progress events are readable while provider calls are in flight.

## Work Items

### 23-01 Core Ledger

- Add `JobDispatchOutbox` model and migration.
- Add repository/service helpers:
  - create dispatch row for a job
  - list pending dispatch rows
  - mark dispatched/failed idempotently
  - conditionally claim queued jobs
- Add focused core tests for state version and outbox behavior.

### 23-02 API Dispatch

- Add a post-commit dispatcher helper.
- In generation, iteration, and retry routes, write the outbox row in the same transaction as the job.
- Return queue metadata when the dispatcher succeeds after commit.
- Keep idempotent reused jobs from creating duplicate outbox rows.
- Add API tests proving enqueue is not called before commit and pending outbox can be replayed.

### 23-03 Worker Short Transactions

- Claim the job in its own transaction and commit `running`.
- Do provider planning/model-run setup in short committed units.
- Call provider outside a transaction.
- Write staging object outside DB transaction, then create artifact/version/model-run completion and job success in one short transaction.
- On failure, open a fresh transaction and persist model run failure/job failure event.
- Add worker tests proving duplicate claims do not double-run and `running` is visible while the provider awaits.

## Risk Notes

- SQLite test coverage should avoid row locking features unavailable in SQLite; use conditional `UPDATE ... WHERE status='queued'`.
- Object storage writes can still happen before DB finalization; use unique object keys and persist failure events if DB completion fails.
- Keep old queue response shape stable for frontend and generated contracts.
