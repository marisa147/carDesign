# Phase 3 Research: First Text-To-2D Generation Slice

**Date:** 2026-06-17
**Status:** Ready for planning

## Research Questions

1. What is the safest implementation shape for first text-to-2D generation given the Phase 2 ledger?
2. Which provider strategy should Phase 3 plan around without locking the product to one vendor?
3. What validation evidence is required to claim `GEN-01` through `GEN-07` are covered?

## Source Notes

### OpenAI Images API

Official docs describe image generation through the Responses API image generation tool and Images API, with current image model options including `gpt-image-2`, `gpt-image-1`, and `dall-e-3`. The docs also call out model output differences, token/cost behavior for GPT Image models, and unsupported options by model. Source: https://platform.openai.com/docs/guides/image-generation

**Planning implication:** OpenAI is a viable adapter candidate, but exact model selection and pricing should stay config-driven. Do not hard-code old model names or assume cost fields map cleanly to image count only.

### Black Forest Labs FLUX API

Official BFL docs describe an asynchronous API shape: submit a generation task, poll for completion, and retrieve result URLs. BFL notes signed URL behavior and expiry, so outputs should be downloaded and persisted by the application. Source: https://docs.bfl.ai/

**Planning implication:** BFL aligns well with the existing asynchronous worker model. If selected as the first hosted adapter, the worker must poll with a timeout, sanitize provider errors, and copy generated bytes into project object storage immediately.

### fal.ai Queue Pattern

Official fal docs recommend queue-backed `submit` for production-style long-running generation requests and expose request status/result patterns. Source: https://fal.ai/docs

**Planning implication:** fal is another adapter candidate, but Phase 3 does not need multiple hosted adapters. The provider interface should support submit/poll/result flows so a fal adapter can be added later without schema changes.

## Recommended Provider Scope

Phase 3 should implement:

1. `local-deterministic` provider, required for tests, Docker smoke, and no-key development.
2. One hosted adapter behind explicit settings and mocked tests. Prefer BFL first because its async task model maps naturally to Celery and `AI_PROVIDER_BFL_API_KEY` already exists in env examples.
3. Adapter interface general enough to add OpenAI or fal later without changing API/job contracts.

Phase 3 should not implement three hosted providers at once. That would expand verification and operational surface before the first concept loop is proven.

## Architecture Findings

- Phase 2 already has the needed durable primitives: `DesignBrief`, `GenerationJob`, `JobEvent`, `ModelRun`, `Artifact`, and `DesignVersion`.
- Existing `jobs.create_model_run`, `jobs.create_artifact`, and `jobs.create_design_version` can be reused with small extensions rather than adding new tables.
- Existing `assets.require_confirmed_rights` can enforce the reference-asset rights gate.
- Current `ObjectStorage` only supports `put_object`, which is sufficient for generated outputs if the worker receives provider bytes.
- Worker dependencies currently lack `httpx` and `Pillow`; these should be added only to `services/worker`.
- FastAPI route handlers should continue to be thin and should not own provider execution.

## Prompt Planning Findings

A useful Phase 3 `PromptPlan` should include:

- Original user request.
- Normalized brief fields.
- Supported vehicle template id and view.
- Unsupported-field warnings.
- Reference asset metadata and object keys, never raw secrets.
- Final prompt text exactly as sent.
- Provider/model/parameter block.

The prompt planner should be deterministic and testable. AI-based brief parsing can be added later after the image path and eval dataset exist.

## Validation Architecture

### Must-Have Truths

1. A natural-language request can become a typed structured brief.
2. Unsupported template/view requests are normalized with visible warnings.
3. Generation creates or reuses a durable job with idempotency protection.
4. Worker execution records prompt/provider/model trace in a model run.
5. Successful local generation stores a real image artifact and generated design version.
6. Missing-rights reference assets never reach provider execution.
7. Provider failures produce durable failed job state and retryable behavior.

## Security And Safety Notes

- No API keys in browser code, job events, model-run prompt payloads, or docs.
- Hosted provider calls require explicit `AI_PROVIDER_CALLS_ENABLED=true`.
- Bounded polling/timeouts prevent runaway worker tasks.
- Provider errors must be sanitized before user-visible events.
- The generated output should be labeled as a concept preview, not production-ready wrap art.

## Planning Recommendation

Plan Phase 3 in seven executable slices:

1. Typed brief contracts and core parser.
2. Template catalog and deterministic prompt planner.
3. Provider adapter interface, local deterministic provider, and hosted adapter scaffolding.
4. Worker generation pipeline with durable artifact/model-run/version records.
5. API routes for brief review, generation submission, and retry.
6. Contracts and minimal frontend proof.
7. Smoke, docs, verification report, and Phase 3 UAT checklist.
